# 登入權限與路由控制 & AI 聚餐選餐廳 產品修改規格書 (PRD)

> 更新日期：2026-09-01
> 本版整合「登入權限與路由控制」「我的聚會彈窗過期機制」最新規格，並與既有 PRD 合流。

---

## 1. 產品核心願景與範疇定義 (Product Vision & Scope)

本產品定位為精準解決「聚餐選餐廳」痛點的 AI 輔助決策工具。在初期戰略評估中，我們將產品範疇由「泛型活動推薦」收斂至**「AI 專業選餐廳」**。此決定不僅是為了避開與 A 組「菜單功能」的重疊，更是為了將開發資源集中於解決「眾口難調」的核心問題。

### 範疇收斂說明

- **捨棄功能**：剔除「泛型行程規劃」與「聚會後自動分帳／菜單 OCR」。主因在於行程推薦的資料源過於破碎，而分帳與 OCR 功能之技術變數（如辨識品質）易延誤開發時程。
- **觸發機制定義**：功能啟動必須在「活動時間與人數已敲定／成團」後，由主揪手動發起。系統不介入前期的揪團投票，而是專注於「成團後」的精確決策。

### 戰略評估 (Strategic Rationale)

透過範疇收斂，開發團隊能顯著縮短開發週期（Time to Market），並透過專屬餐廳的加權模型提升 AI 推薦精準度。這讓產品能以最輕量化的架構，達成最高頻率的使用者需求。

## 2. 登入機制與路由控制 (Authentication & Routing) — 本次更新重點

### 2.1 主站管理頁 (`https://ooxx.com`) ➔ 強制 Google 登入（主揪）

**登入技術選型評估**

小組在會議中針對不同的登入技術與成本進行了深度評估，最終決定排除其他方式、只保留 Google SSO，核心考量如下：

- **排除「自建帳戶密碼」**：如果自建帳密，系統未來必須額外處理「忘記密碼」、「修改密碼」、「信箱驗證」等繁瑣安全流程，這對現階段的時程來說開發成本極高。
- **排除「手機簡訊 OTP 驗證」**：技術上需要額外串接外部簡訊平台，且發送簡訊的費用負擔過重，因此予以捨棄。
- **排除「安全提示問題」**（如：國小唸哪裡）：這本質上還是必須走註冊與資料庫比對流程，並未簡化開發難度。
- **「Google SSO」的決定性優勢**：主揪只需要按一個按鈕就能一鍵登入，完全不用再記一組新的帳密。最重要的是，Google 的 SSO 機制會把所有身分安全驗證、帳號管理等繁重成本全部代為處理，對工程師團隊（B 組）來說是實作難度最低、也最安全的折衷方案。

因此，規格書中明確將主揪登入機制限制在 **Google SSO 獨佔**，不開放其他註冊／登入管道。

**存取控制與登入流程**

- 使用者訪問主網址時，若為未登入狀態，頁面上會顯示一個按鈕，點擊後導向 Google OAuth 跳轉登入。
- 登入完成導回站內後，前端記下取得的 token，再導向主控台；此時才視為「已登入」狀態，才可進行「發起聚會／創建活動」或瀏覽過往活動。

**登入後首頁配置**

針對已登入後應呈現的頁面，討論了兩個方向：

- **選項 A**：進到「我的活動」列表頁，最上方放一個「新增活動」按鈕。
- **選項 B**：頁面分成兩大塊 —— 一塊是醒目的「建立活動」大按鈕，另一塊是「我揪的團」過往揪團紀錄。

> **已定案採選項 B**：頁面分成「建立活動」大按鈕與「我揪的團」過往揪團紀錄兩大塊。

**Header UI 規格**

- 登入後，右上角顯示主揪的 Google 頭像。
- 點擊頭像：展開下拉選單，提供「登出」功能，登出後重定向回主站登入頁。
- Header 為全站共用元件，需固定顯示於所有登入後頁面的最上方（含建立活動頁、活動列表頁、活動詳情頁等），不隨頁面切換而消失，維持登入狀態與登出入口的一致性。

### 2.2 活動專屬頁 (`https://ooxx.com/{roomId}`) ➔ 完全免登入（參與者）

- 團員（參與者）點擊專屬網址進入該活動頁面時，完全不需要登入即可進行投票、檢視活動詳情。

**參與者是否需要填寫 Email？**

- 不強制填寫，一律採「選填」方式。
- 核心考量：參與者對新平台尚未建立信任感，若被要求強制登入或填寫過多個人資料，容易產生防備心，甚至懷疑是詐騙或釣魚網站。為降低使用門檻、不阻礙投票流程，被揪者一律免登入，Email 欄位僅作選填。

**現階段的通知規劃**

現階段採取「填了才發，不填就算了」的極簡輔助模式，通知並非第一階段的研發重心：

- **以主揪聯絡為主，系統為輔**：本產品定位為輔助的外掛工具，而非完全取代既有通訊軟體。活動定案的通知與資訊同步視為主揪的責任，主揪可自行在 LINE 群組等管道提醒聯絡大家。
- **有填才通知**：系統的 Email 通知僅作輔助性質。參與者若有填寫 Email，活動時間定案時系統會發送通知；未填寫則不寄送，需自行記住時間。
- **開發時程安排**：第一階段核心目標是「減輕開發負擔、先約得成」，更完善的通知與資訊同步功能規劃於後期 Roadmap。

### 2.3「我的聚會」彈窗 — 過期自動隱藏

配合現行「活動連結有效期限為 7 天」的規則，過期活動需自動清理，避免主揪列表出現失效項目。

**判斷機制**

- 以「活動建立時間」起算，**+7 天**為有效期限。
- 超過 7 天（連結失效）的活動，需自動從主揪的「我的聚會」列表中移除，不再呈現，確保列表僅呈現有效活動。

### 2.4 主揪 (Host) 權限管理

- **Google SSO 整合**：放棄自建帳密或 OTP（簡訊驗證成本約每則 0.6–0.7 元），直接整合 Google SSO 以降低開發負擔並確保 API 額度控管。
- **功能**：提供個人聚會紀錄管理，並允許主揪在不同活動中使用不同暱稱（江湖名稱）保護隱私。

### 2.5 資料生存週期

- 所有活動連結與資料於 7 天後自動失效（自「我的聚會」列表隱藏、參與者頁面停止服務）。
- 此設計基於討論共識：7 天足以涵蓋活動後續照片分享、失物招領等需求，同時落實資安防護。
- **刪除方式建議採「軟刪除」（soft delete）**：到期資料僅標記為失效、不做實體刪除。若採硬刪除，日後新建活動產生的 roomId 有機率與曾經存在過的舊 ID 重複，可能導致資料衝突或誤連結到舊活動；軟刪除可保留 ID 佔用紀錄，避免此問題，未來也保留清運（如真正清除或封存）的彈性。

### 戰略安全考量 (Strategic Security Rationale)

強迫主揪使用 Google SSO 可有效防止惡意修改紀錄，並降低後端儲存負擔；對參與者採取免登設計，則是極大化易用性，讓揪團過程保持零阻力。

## 3. 前端介面設計：複合式標籤與輸入系統 (Frontend Interaction Design)

為捕捉使用者的細微意圖，介面採用「模組化標籤 (Tags)」結合「自訂文字框 (Prompt)」的設計。標籤系統能快速建立需求骨架，文字框則賦予表達彈性，減少 AI 誤解需求的風險。

### 標籤與需求參數表

| 類別 | 選項內容 | 備註 |
|---|---|---|
| 地理範圍 | 步行距離（800m / 15 分鐘）、捷運沿線（如：藍線沿線）、特定行政區 | 解決「不要離車站太遠」的硬性痛點 |
| 與會關係 | 同事、朋友、家人、社團、約會 | 決定 AI 推薦的氛圍與桌型配置（如：大桌或安靜環境） |
| 預算區間 | <200、200-400、400-600、600-800、800-1000、>1000 | 對應 Google Maps 價格級距 |
| 人數規格 | 2 人、3-4 人、5-8 人、9 人以上（多人）、20 人以上（團體） | 篩選具備對應容納量或包廂的餐廳 |
| 硬體與情境 | 可久坐、有插座（解決手機低健康度耗電痛點）、停車位、親子友善、無障礙 | 針對 iPhone 12 等低電池健康度使用者提供輔助 |
| 飲食偏好 | 素食、辣度（不吃辣／愛吃辣）、特定料理（美式／日式／韓式） | 基礎篩選條件 |

### Prompt 組合與技術封裝

前端將捕捉到的標籤狀態封裝成結構化的 JSON 格式傳送至後端。例如，選中 `#同事` 標籤時，系統會自動在 System Prompt 加入：「優先篩選安靜環境、適合專業討論且具備大桌配置的餐廳」。

> **待釐清項目**：目前的標籤 → Prompt 組合與封裝方式仍是初步設計，實際能否穩定轉換成 AI 可理解、可執行的查詢條件尚未驗證，後續需要進一步優化調整並實測。
>
> 另外，「捷運沿線找餐廳」（地理範圍標籤之一）在技術上是否可行也待確認：若後端推薦邏輯採用**方案 B**，有機會透過該方案的地理搜尋能力達成，但仍需進一步確認 Google Places API（或其他第三方地圖／地點 API）的用量限制、計費方式，以及單次查詢實際能回傳的資料筆數上限，待確認後才能定案此標籤的實作方式。

### 戰略 UX 影響 (Strategic UX Impact)

標籤化設計能引導使用者提供關鍵決策參數，避免盲目搜尋。特別是針對「有插座」或「步行 800m 內」等細節標籤，能有效解決如手機電量不足（I12 痛點）或交通不便導致的聚會流失率。

## 4. 後端架構與 AI 推薦邏輯 (Backend & AI Recommendation Logic)

後端採用 A/B 方案評估策略，在 Prototype 階段優先考量技術成本與資料實時性。

### 技術方案評估

- **方案 A（Google Places API + LLM）**：撈取附近 20 筆 Nearby Search 結果，交由 Gemini 進行加權排序。優勢在於成本控制（Google 提供每月 5,000 至 10,000 次的免費 API 額度），適合 Prototype 快速驗證。
- **方案 B（Perplexity RAG）**：直接調用 Perplexity API。優勢在於其 RAG 實時網頁搜尋能力，能擷取最新的部落格評價或「隱藏版美食」，而非僅依賴 Google 的靜態元數據。

### 推薦呈現規範

- **輸出限制**：最多顯示前 5 名推薦（核心推薦為 3-5 名）。
- **核心指標**：現階段**暫不做「適合度百分比」**這項指標。原因是評分標準（如何量化「適合度」）仍需反覆調校，若貿然上線，可能還要再疊加一層 AI 呼叫專門去評比適合度百分比，徒增 API 用量與複雜度，現階段效益不明確，故先擱置。
- 「重述需求」功能（Restate Requirements）仍保留，用以驗證 AI 理解度；若 AI 理解有誤，使用者可調整標籤重新計算。

### 戰略技術價值 (Strategic Technical Value)

加權評分機制（地點、預算、評價總和 100%）將 AI 的感性建議數據化，提升主揪採納推薦的信任感。Prototype 階段優先使用免費額度 API，可確保開發預算保留給後續的 RAG 深度整合。

## 5. 通知系統與輔助工具 (Notifications & Helpers)

通知全面定位為「Nice-to-have」輔助，以不干擾使用者為核心原則：僅在正常流程有達成對應條件時才觸發寄信與排程，不特別為通知另外設計流程或提高優先權。

### 觸發機制與功能

- **通知點**：「活動定案」、「Deadline 到期」、「留言板更新」，僅針對有提供 Email 的參與者發送。
- **Google 行事曆整合**：已於前端實作完成，採 Frontend-generated URL（Data URI）方式，在前端直接產生行事曆連結供使用者一鍵加入，完全不依賴後端 API 或 Email 寄送，大幅降低系統複雜度。

### 戰略 UX 影響 (Strategic UX Impact)

「免登入即可紀錄行程」與「前端行事曆整合」的組合，能在不增加後端負擔的前提下，顯著提升使用者的回訪率與活動成團率。

## 結語

本規格書旨在建立共識基準，導引工程師精準實作 AI 推薦邏輯與 SSO 安全機制，確保 B 組開發項目能如期、高品質產出。本次更新聚焦於登入首頁配置定案、標籤 Prompt 封裝與捷運沿線搜尋待釐清事項、AI 推薦適合度百分比暫緩、通知與行事曆整合現況說明，並移除原第 6 章（工程合流與 RD 溝通策略）。
