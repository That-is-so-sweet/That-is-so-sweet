# AI選餐廳｜Perplexity 串接執行計畫書

> 揪甘心──工程執行文件
> 版本：v1.0　日期：2026-09-02
> 定位說明：本文件是「AI選餐廳」功能中，Perplexity 串接這一段的執行計畫書，彙整目前測試結果與技術調查所得，提供工程組作為開發依據。內容將於後續整併進主要的《AI推薦（選餐廳／活動／行程）功能規劃書》。

## 一、目的與範圍

本文件回答三個問題：要打 Perplexity 哪一種 API、Prompt 該怎麼設計才能穩定產出結構化資料、以及資料串接時（尤其是店家連結）該怎麼處理才不會出現錯誤或編造的資訊。範圍僅涵蓋「AI選餐廳」（AI推薦功能的 Lv.1）與 Perplexity 之間的串接，不含 Google Places API 的串接（見主規劃書第八節，兩者為互相備選的資料來源方案，本文件記錄的是 Perplexity 這條路線的執行細節）。

## 二、API 選型

**結論：串接 Agent API（`Create Agent Response`），不使用 Router API（`Create Chat Completion` / `Create Response`）。**

判斷依據：

1. **時效性**：Perplexity 已公告 Sonar 系列（舊的 Chat Completions 對話式 API）將於 **2026 年 9 月 27 日**停止支援，官方建議全面遷移至 Agent API。現在開發應直接從 Agent API 起手，避免上線後短期內又要改版。

2. **搜尋能力是否內建**：Agent API 官方文件明確示範「網路搜尋能力＋json schema 結構化輸出」搭配使用的做法，等於官方就是把它設計成「搜尋＋結構化輸出」一起用的組合，符合我們「依條件即時搜尋餐廳→輸出固定格式結果」的需求。

   相對地，Router API 底下的 `Create Response` 端點雖然同樣支援 `response_format` 的 json_schema 結構化輸出（strict mode），但文件中的 `tools` 參數指的是開發者自訂的 function tools／custom tools，並未提及內建的網路搜尋工具；若採用這條路線，需要自行額外串接搜尋工具（例如用 function calling 接 Google Places API）才能確保資料即時性，等於多一層工程複雜度，且官方沒有明確示範過這種組合的穩定性。

3. **其餘 API 類型不適用**：Search API（`Search the Web`）只回傳原始搜尋結果，沒有 LLM 幫忙整理、排序、產生推薦理由，需要自己再做一層加工；Embeddings API 是語意向量比對用途，與本功能需求無關。

**如果日後 Agent API 測試中遇到限制或效能瓶頸，備案是評估 Router API＋自行串接 Google Places API 作為搜尋工具**，但這不是第一版建議路線。

## 三、為什麼不能只用 Perplexity 網站的對話框測試上線

在 perplexity.ai 網站的聊天框直接測試時，即使 prompt 裡要求輸出純 JSON，仍會偶爾夾雜額外的說明文字或格式跑掉，這是**正常現象**，因為對話介面沒有任何參數在強制格式，模型只是「盡量照指示做」，沒有強制力。

正式串接必須透過 **API 呼叫**，並在請求中帶入 `response_format` 參數、設為 `json_schema` 類型：官方文件說明，只要用這個類型，輸出會**強制符合定義好的 schema（strict mode）**，不會再夾雜其他文字。這是解決格式問題的正確做法，不能只靠在 prompt 文字裡拜託模型「請輸出純 JSON」。

## 四、關鍵限制：不要讓模型自己生成網址

官方文件明確警告：**不要在 JSON schema 裡要求模型自己生成連結**（例如店家的 Google Maps 網址），因為模型把 URL 當作結構化輸出的一部分時，容易生成格式錯誤或編造的連結。

這一點在實際測試中也得到印證（詳見第七節「已完成的實測與觀察」）：早期版本要求模型自行組出 Google Maps 網址，結果用經緯度座標查詢，這種查詢方式不一定能穩定連到正確的店家頁面。

**正確做法**：JSON schema 裡完全不要求模型填寫網址欄位，模型只需要確保 `name`（店名）與 `address`（地址）完整正確；真正的來源網址，改由**後端從 API 回應中另外附的 `citations` 或 `search_results` 欄位取得**——這兩個欄位是 Perplexity 系統做網路搜尋時自動夾帶的真實引用來源，不是模型生成的內容，可信度高很多。後端邏輯是用每筆結果的 `name` 去匹配 `citations`／`search_results` 裡對應的來源，取出真實連結後再組進回傳給前端的資料裡。

## 五、資料流程（給工程組的整體邏輯）

1. 前端／後端組出 User Prompt（依偏好模組蒐集到的條件動態帶入，見第七節樣板）。
2. 呼叫 Agent API 的 `Create Agent Response`，帶入 System Prompt、User Prompt，並在請求中設定 `response_format` 為第六節定義的 json_schema（strict mode）。
3. 取得回應後，解析 `restaurants` 陣列（結構化的候選餐廳清單，不含網址）。
4. 同時解析回應中的 `citations`／`search_results` 欄位，用每筆結果的 `name` 做比對，取得對應的真實來源網址。
5. 將步驟 3、4 的結果合併成最終資料（含網址），回傳給前端顯示為候選卡片。
6. 若步驟 4 比對不到對應網址（例如名稱比對失敗），該筆結果的網址欄位顯示為空，前端需設計對應的容錯呈現（例如只顯示地址與電話，不顯示「查看地圖」按鈕），不可以由前端或後端自行拼湊一個網址頂替。

## 六、System Prompt（正式版）

```
你是「揪甘心」App 的餐廳搜尋助手。你的任務是根據使用者提供的條件，搜尋真實存在、目前仍在營業的餐廳，並回傳結構化的推薦結果。

嚴格規則：

1. 只能推薦你能透過搜尋確認目前仍在營業的真實餐廳，絕對不可以編造餐廳名稱、地址或任何資訊。

2. 每一筆結果都必須包含以下完整欄位，缺一不可：
   - name（店家名稱，需完整、正確，因為後端會用這個名稱去比對 citations 取得真實網址，名稱務必準確）
   - rating（目前 Google 評分，格式如 4.5，若查不到請填 null）
   - review_count（評論數量，若查不到請填 null）
   - opening_hours（目前營業時間，格式如「週一至週日 11:00–21:00」，若查不到請填 null）
   - price_range（價位等級，用 $ / $$ / $$$ / $$$$ 表示，若查不到請填 null）
   - avg_price_per_person（每人平均消費金額，格式為 {"min": 數字, "max": 數字}，單位新台幣，若查不到請填 null，不要把這個資訊只寫在文字敘述裡）
   - address（完整地址）
   - phone（聯絡電話，若查不到請填 null）
   - cuisine_type（料理類型，如日式、東南亞料理、火鍋等）
   - distance_info（距離資訊，格式為 {"transit_point": "最近的捷運站或地標", "walk_minutes": 數字}，若無法確認實際步行時間，walk_minutes 請填 null，不可以自行估算後當作確定數字寫入）
   - recommend_reason（1–2 句話的推薦理由，必須具體指出這間店「哪一項菜單特色」符合使用者條件，例如指出具體菜色或菜單分類，不可以使用空泛或跟其他餐廳重複的套句）

3. 【重要】不要在這份 JSON 裡自行生成或填寫任何網址（包含 Google Maps 連結）。網址一律由呼叫端另外從這次回應所附的 citations／search_results 欄位裡比對取得，你只需要確保 name 與 address 完整正確，方便後續比對。

4. 若某個欄位查不到確切資訊，請填 null，絕對不可以用推測或常識去填補，寧可留空也不可以編造。

5. 回傳的餐廳數量必須是 3 到 5 間。若在指定地理範圍內符合條件的餐廳不足 3 間，才可以放寬地理範圍搜尋，且必須確保放寬後的搜尋範圍，與實際回傳結果的地址真的對應得上——不可以說已放寬範圍，但回傳結果的地址其實都還在原本範圍內；也不可以放寬範圍卻不在 notes 說明。

6. notes 欄位只能填寫「這次搜尋過程中實際發生的事」（例如是否真的放寬了地理範圍、是否有條件因搜尋不到而放寬），不可以填寫制式化、與實際搜尋結果對不上的說明文字。若沒有任何調整，notes 請填 null。

7. 輸出格式必須是純 JSON，不要加任何 JSON 以外的文字、不要用 markdown 的程式碼區塊符號包起來，結構如下：

{
  "restaurants": [
    {
      "name": "",
      "rating": null,
      "review_count": null,
      "opening_hours": "",
      "price_range": "",
      "avg_price_per_person": {"min": null, "max": null},
      "address": "",
      "phone": null,
      "cuisine_type": "",
      "distance_info": {"transit_point": "", "walk_minutes": null},
      "recommend_reason": ""
    }
  ],
  "notes": null
}
```

**API 呼叫端提醒**：請將上述 JSON 結構設定為 `response_format` 參數中的 `json_schema`（`name`／`address` 設為必填欄位），呼叫時會自動以 strict mode 強制輸出符合 schema，不需要再靠 prompt 文字拜託模型輸出純 JSON。

## 七、User Prompt 樣板與範例

**樣板**：

```
請根據以下條件，搜尋並推薦 3 到 5 間符合的餐廳：

【地點】{{地點或區域，例如：台北市大安區}}
【人數】{{與會人數，例如：8 人}}
【料理偏好】{{料理大分類與細節，例如：亞洲料理，偏好日式或東南亞}}
【忌口／過敏】{{若有，例如：其中 1 人不吃牛肉、1 人對花生過敏；若無請填「無」}}
【預算區間】{{例如：每人新台幣 400–800 元}}
【與會關係】{{例如：同事聚餐}}
【是否有攜帶孩童】{{是／否}}
【可接受距離】{{例如：捷運站步行 10 分鐘內}}

請務必確保：
- 每間餐廳目前仍在營業，不要推薦已歇業的店家。
- 這間餐廳的座位或空間規模足以容納 {{人數}} 人（例如避免推薦只有吧檯座位的小店給大團體）。
- 若有忌口／過敏條件，recommend_reason 請具體指出菜單上「哪一類菜色」可以避開該條件，而不是只寫「可避開牛肉」這種空泛描述。
- 各筆結果的 recommend_reason 彼此之間不可以使用重複或高度相似的句型，每一筆都要反映該餐廳的實際特色。
- distance_info 的 walk_minutes 若無法確認實際步行時間，請填 null，不要自行估算。
- 若地理範圍有實際放寬，請確保回傳結果的地址跟放寬後的範圍相符，並在 notes 如實說明；若沒有放寬，notes 請填 null。

請直接輸出符合 System Prompt 規定格式的 JSON，不要有其他文字。
```

**範例（依實測情境帶入）**：地點台北市大安區、8 人同事聚餐、料理偏好亞洲料理（偏好日式或東南亞）、忌口為 1 人不吃牛肉、1 人對花生過敏、預算每人新台幣 400–800 元、無攜帶孩童、可接受距離為捷運站步行 10 分鐘內。將上述變數依樣板格式帶入即可直接測試。

## 八、已完成的實測與觀察

初版 Prompt（尚未套用第四節「不要求模型生成網址」的修正前）實際丟入 Perplexity 測試，取得 4 筆結果，人工核對後發現以下問題，本文件第六節的正式版 System Prompt 已針對這些問題做出對應修正：

| 觀察到的問題 | 對應修正 |
|---|---|
| `google_maps_url` 用經緯度座標查詢，連結不穩定，有時無法直接跳到正確店家頁面 | 完全移出 JSON schema，改由後端比對 citations／search_results 取得真實網址（見第四、五節） |
| `notes` 欄位說「已放寬地理範圍至信義區、中山區」，但 4 筆結果實際地址全部都在大安區，說明與實際結果不一致 | System Prompt 第 5、6 條規則明確要求 notes 只能寫「實際發生的事」，且需與回傳結果地址一致 |
| `recommend_reason` 有 3 筆用了幾乎相同的句型（「可避開牛肉並選擇無花生料理」），個別化程度不足 | System Prompt 要求具體指出菜單特色，且同批結果不可重複句型 |
| 距離／交通時間資訊（如「步行約 8 分鐘」）混在推薦理由的文字敘述裡，不利前端拆解顯示 | 拆成獨立的 `distance_info` 結構化欄位，且不確定時明確要求填 null，不可自行估算 |
| 價位僅有 `$` 符號等級，缺乏具體金額數字，無法用於精準預算比對 | 新增 `avg_price_per_person` 結構化欄位（min／max 數字） |

## 九、工程組執行建議

1. **第一步**：先用第六、七節的 Prompt，透過 Agent API 的 `Create Agent Response` 端點搭配 `response_format(json_schema, strict)` 做小規模測試（建議至少涵蓋 5 組不同條件：不同人數、不同料理偏好、有無忌口、地理範圍是否需要放寬），確認輸出穩定符合 schema。
2. **第二步**：實作「用 `name` 比對 `citations`／`search_results` 取得真實網址」的後端邏輯，並人工核對比對出的網址是否真的連到正確店家頁面；同時設計比對失敗時的前端容錯呈現。
3. **第三步**：確認以上兩步穩定後，才加入正式的容錯處理（JSON 格式異常時的重試機制、API 逾時或錯誤時的降級呈現，例如退回「當地最適合＋人數」的預設推薦邏輯，銜接主規劃書第五節的預設模式設計）。
4. **第四步**：與主規劃書第八節（Google Places API 方案）做效果與成本比較後，再決定正式採用哪一條資料來源路線，或是否兩者並行（例如 Perplexity 負責生成推薦理由與排序，Google Places API 負責驗證店家仍在營業與提供穩定的地圖連結）。

## 十、待確認事項

- Perplexity Agent API 本身的呼叫計費方式與費用，需要另外估算，本文件尚未涵蓋（先前規劃書中的費用估算是針對 Google Places API 方案）。
- `citations`／`search_results` 欄位在實際回應中的確切資料結構（欄位名稱、是否穩定包含每間餐廳的來源），建議工程組第一步測試時同步記錄實際回應範例，確認比對邏輯可行。
- 若日後決定同時保留 Google Places API 與 Perplexity 兩條路線，兩者的資料格式需要統一，由誰負責定義最終共用的資料結構，需要團隊內部先拍板。
