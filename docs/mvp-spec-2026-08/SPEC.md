## 1. Background 背景

### 1.1 產品定位

**揪甘心** — 聚會時間協調工具。核心主張：參與者免登入、免加好友，透過一個連結就能勾選可行時段；主揪（發起人）可以一鍵彙整所有人的時間、看熱點圖、拍板定案。

### 1.2 核心問題與商業假設

**痛點（Who & Why）**
主揪在揪團前期需要反覆詢問、手動整理每個人的可行時間，平均花 5 天、來回問好幾輪才能定案；參與者則因為要開行事曆確認、打字回覆而拖延，甚至因行程未定而錯失參與機會。

**核心商業假設（Value）**
如果我們用「時間投票連結」取代「LINE 群組人工喬時間」，主揪能將喬時間的決策時間從平均 5 天縮短，參與者也會願意用勾選取代打字回覆，不需要加好友、不需要開行事曆手動比對。

**假設的推翻條件**（工程與產品要持續關注的訊號）
- 如果受訪主揪普遍認為「在 LINE 群組裡問一下」比「打開新連結」更省事 → 遷移成本蓋過新體驗價值
- 如果多數參與者仍傾向直接在群組留言回覆，而非使用勾選介面 → 核心互動機制假設不成立

**驗證方式**：先用 concierge MVP（人工整理 + 簡單表單 / prototype）驗證核心假設，不必等自動比對演算法做完整。這個核心假設已經用一版純前端 prototype 驗證過互動流程並收集了初步 UX 回饋（見文末附錄、`docs/ux-feedback-2026-08/PLAN.md`），現在要進入正式開發階段：具備完整後端、資料庫的產品，而不是延續 prototype 的架構。

### 1.3 產品原則

> 先讓活動能成團，再優化活動體驗。第一階段聚焦驗證「喬時間」這個核心假設。

對應到開發優先序：**Phase 1** 只解決「約得成」——降低成團阻力的核心必要功能；活動體驗的加值功能（聊天室、選餐廳、分帳等）留到後續階段，見第 2 節 Roadmap。

### 2.1 本文件範圍界定

本文件是**正式產品的完整範圍藍圖**，涵蓋前端、後端、資料庫、通知等所有應具備的系統組成。但**詳細到「可直接開工」程度的功能規格，只寫到 Phase 1（Must-have）**；Phase 2、Phase 3 在第 2.4 節僅列方向與範圍說明，等 Phase 1 上線後再個別產出詳細規格文件。

| 系統組成 | 正式產品範圍 |

### 2.3 Phase 1（Must-have）明確範圍

對應 Roadmap「階段一｜降低成團阻力」，本階段要完整實作並上線的功能：

1. 主揪發起活動，系統自動產生可分享連結
2. 參與者透過連結免加好友、免登入即可勾選可行時段
3. 系統自動彙整所有人勾選結果，篩出共同可行時段
4. 主揪可查看彙整結果並一鍵確認最終時間
5. 確認後系統自動通知所有參與者

這 5 項在第 4 節會展開為完整的功能需求（FR-1 ~ FR-N）。

### 2.4 Should-have（Phase 1 候選加值項，非必要）

不影響核心問題是否解決，產品沒有它也能動，**視 Phase 1 開發資源決定是否納入**，本文件不展開詳細規格：

- 未回覆者的提醒通知
- 時段衝突時的次佳選項建議

### 2.5 Won't-have（明確排除，屬於 Phase 2 / 3 或更後期）

**Phase 2｜減輕主揪壓力**：快閃聊天室、AI 選餐廳、分帳功能
**Phase 3｜提升聚會體驗**：飲食護照、菜單翻譯、邀請函等進階功能
**未列入任何階段但被明確排除**：跨平台行事曆同步（自動雙向同步；單向「加入行事曆」的匯出連結不在此排除範圍內，是可視情況併入 Phase 1 的小功能）

這些項目**這次不需要展開規格**，僅在此記錄，避免 Phase 1 開發時範圍蔓延（scope creep）。

## 3. User Story / Use Case

### 3.1 角色定義

- **主揪（Host）**：發起活動的人，擁有查看彙整結果、定案、取消、重開活動的權限
- **參與者（Participant）**：透過分享連結進入活動、勾選可行時段、留言的人（免登入）

### 3.2 現況使用者旅程與痛點

**主揪旅程**：
1. 發起邀約：「耶！找大家一起來玩」
2. 喬時間耗費大量溝通成本：「只是約一個活動，為什麼像在開會？」
3. 成員回覆率低，活動停滯：「到底誰什麼時間可以？」
4. 活動當天很開心
5. 群組收尾：主揪承擔所有行政工作，「下次不要我揪好了…」

**參與者旅程**：
1. 不知道怎麼回覆時間：「我要查一下行事曆，晚點再回好了」
2. 不知道其他人的選擇狀況：「大家是真的可以嗎？」
3. 投票後不知道是否確定：「所以哪一天時間會確定下來？」
4. 活動當天很開心
5. 結束後群組安靜、殘留尷尬

Phase 1 的功能需求（第 4 節）直接對應解決旅程中第 2、3 步的痛點：溝通成本高、回覆率低、投票後狀態不明確。第 5 步「群組收尾」的行政負擔與尷尬感，多數留給 Phase 2（快閃聊天室等）處理，不在 Phase 1 範圍。

### 3.3 正式版本使用者故事（Must-have 對應）

- 身為**主揪**，我想要發起活動後系統自動產生一個可分享的連結，這樣我就不用手動整理時間表傳給大家。
- 身為**參與者**，我想要點連結就能直接勾選可行時段、不需要加好友或註冊帳號，這樣我才不會因為門檻太高而拖延回覆。
- 身為**主揪**，我想要一個畫面看到所有人彙整後的可行時段熱度，這樣我不用自己一筆筆對照。
- 身為**主揪**，我想要在看到彙整結果後直接一鍵確認最終時間，這樣定案這件事不用再回群組另外宣布一次。
- 身為**參與者**，我想要在主揪定案後自動收到通知，這樣我才不會錯過已經確定的時間而漏掉活動。

### 3.4 關鍵 Use Case

**UC-1：主揪建立活動**
- 前置條件：無（免登入）
- 主流程：主揪填寫活動名稱、主揪姓名（必填，日後用於身分驗證）、候選時段模式（純日期或指定時間，兩者擇一，建立後不可變更）、候選時段（至少 1 個）、回覆截止時間（必填，以台灣時間認定）、（選填）主揪 Email、地點與說明 → 系統建立活動並產生可分享連結；若填寫了主揪 Email，系統寄送一封含分享連結的通知信
- 例外：候選時段為空、活動名稱或主揪姓名為空、活動名稱超過長度限制、回覆截止時間未填 → 阻擋送出並提示

**UC-2：參與者投票**
- 前置條件：持有有效的活動分享連結，且活動狀態為進行中、投票未截止
- 主流程：輸入暱稱（＋ Email，用於通知）→ 針對每個候選時段勾選可行／可能可以／不可行 → 送出後可回連結修改
- 例外：活動已取消或已定案 → 不接受新投票；投票已截止 → 提示聯繫主揪重新開放

**UC-3：主揪查看彙整並定案**
- 前置條件：輸入的主揪姓名（若活動有登記 Email，需同時輸入 Email）與活動建立時登記的資料完全相符（區分大小寫，不做寬鬆比對），經伺服器端驗證通過
- 主流程：查看彙整熱度 → 選定最終時段（＋備註）→ 確認定案 → 系統通知所有已回覆的參與者
- 例外：選擇的時段不存在於候選清單 → 阻擋；姓名／Email 與登記資料不相符 → 拒絕操作

**UC-4：主揪取消／重新開放活動**
- 主流程：主揪可將已定案活動改回進行中重新收集回覆，或直接取消整個活動並通知已回覆的參與者（同樣需通過 UC-3 的身分驗證）

**UC-5：留言互動**
- 主流程：參與者／主揪可在活動頁面留言，留言會觸發通知寄送（需在畫面明確提示使用者，避免亂打造成無意義通知——此為 UX 回饋 `docs/ux-feedback-2026-08/PLAN.md` 第 4 項已指出的問題，正式規格需一併處理）

## 4. Feature Requirement 功能需求（Phase 1 詳細規格）

### 4.1 功能需求總表

| 編號 | 功能 | 說明 | 驗收標準 |
|---|---|---|---|
| FR-1 | 建立活動 | 主揪輸入標題（必填，≤30 字）、主揪姓名（必填）、候選時段模式（純日期／指定時間，兩者擇一，同一活動不可混用）、候選時段（至少 1 個）、回覆截止時間（必填，以台灣時間 UTC+8 認定）、主揪 Email（選填，填寫後日後身分驗證需一併核對）、活動說明／地點（選填） | 送出後產生全域唯一活動 ID 與可分享連結；若填寫主揪 Email，系統寄送含分享連結的通知信 |
| FR-2 | 分享連結 | 產生的連結需可被任何人（無帳號）開啟並看到活動內容 | 連結不含可被輕易猜測或暴力枚舉的活動 ID；分享連結本身不含任何可用於取得主揪管理權限的資訊（管理權限的取得方式見 FR-5） |
| FR-3 | 免登入投票 | 參與者輸入暱稱＋ Email，針對每個候選時段選擇可行／可能可以／不可行 | 同一參與者可用「暱稱」或未來的識別機制（見第 6 節開放問題）辨識並允許修改既有回覆，而非每次都新增一筆；可行狀態欄位須設計成可擴充的列舉值（目前 3 種：可行／可能可以／不可行），不可用布林值等二元型態實作，以便未來擴充更多狀態 |
| FR-4 | 彙整統計 | 系統即時計算每個候選時段的可行人數、可能可以人數、不可行人數與名單 | 彙整結果需在有新回覆時即時更新（後端運算或前端訂閱皆可，見第 5 節）；純日期模式以「日」為單位彙整，指定時間模式以每個候選時間點分別彙整，兩者皆不涉及時間區間運算 |
| FR-5 | 主揪定案 | 主揪從候選時段中選定最終時段，可附加備註（如集合地點細節） | 僅通過主揪身分驗證（姓名，若活動有登記 Email 則需一併核對，見第 5.4／5.6 節）才能執行；定案後活動狀態變更為「已定案」 |
| FR-6 | 定案通知 | 定案後，系統對所有已留下聯絡方式（Email）的參與者發送通知 | 通知需包含最終時間、地點、備註；發送失敗需可重試或至少記錄失敗（不可靜默丟失） |
| FR-7 | 活動狀態管理 | 支援「進行中」「已定案」「已取消」狀態，及「重新開放投票」 | 狀態轉換規則：已取消／已定案不可再投票；重新開放會清除最終時段設定，並確保回覆截止時間仍在未來（若已過期則自動順延） |
| FR-8 | 留言 | 參與者／主揪可在活動頁面留言 | 送出前需明確提示「留言會觸發通知信」；留言內容長度上限 300 字 |
| FR-9 | 連結有效期 | 活動結束（最終時段日期）超過 7 天後，連結應失效並回傳明確的「已失效」畫面，而非一般錯誤 | 失效判斷邏輯：以最終時段日期為基準，超過 7 天即失效 |

### 4.2 Should-have / Won't-have（僅列項目，不展開規格）

- **Should-have**（Phase 1 資源允許時可納入）：未回覆者提醒通知、時段衝突次佳建議
- **Won't-have**（Phase 2/3 或排除，本次不規劃）：快閃聊天室、AI 選餐廳、分帳、飲食護照、菜單翻譯、邀請函、跨平台行事曆自動同步

### 4.3 非功能需求（NFR）

正式產品因為要處理真實使用者資料（Email）與對外服務（寄信），需要在 Phase 1 一併規劃：

- **資料隱私**：參與者 Email 僅用於通知寄送，需在畫面明確告知用途；不可用於其他行銷或第三方用途
- **主揪身分驗證**：以「主揪姓名（＋活動有登記 Email 時一併核對）」核對取代任何形式的祕密憑證或 token，比對規則見第 5.4 節；伺服器端每次寫入操作（定案／取消／重新開放）都要重新驗證，不可只靠前端狀態放行。此設計是 Phase 1 刻意接受的風險——未登記 Email 的活動，任何知道主揪姓名（＋活動連結）的人都能取得管理權限，見第 5.6 節與第 6 節開放問題
- **時區**：所有時間一律以台灣時間（Asia/Taipei, UTC+8）認定與顯示，畫面需明確標示「以上時間為台灣時間」；不做使用者地理位置偵測
- **防濫用**：投票、留言等公開寫入端點需有基本流量限制（例如同一 IP／來源在短時間內的請求次數上限），避免灌票或洗版；具體門檻待技術選型後決定，見第 6 節開放問題
- **可用性**：核心投票流程（開啟連結 → 勾選 → 送出）需在行動網路環境下仍可順暢完成，對應「免登入、跨平台」的產品定位
- **資料保存**：活動資料的保存期限（尤其是連結失效後）需要有明確政策，見第 6 節開放問題

## 5. 建議技術架構（草案，待工程團隊定案）

> 這一節是**建議方案**，非最終決策——因為目前尚未決定技術棧，以下依據 Phase 1 功能需求推導出一組合理方案，供工程團隊 kickoff 時討論調整。

### 5.1 架構總覽

```
[瀏覽器 SPA / 前端]  →  [後端 API 服務]  →  [關聯式資料庫]
                              ↓
                       [通知寄送服務]（Email，見 5.5）
```

前端可沿用 React + Vite 架構，並延續文末附錄列出的既有互動設計；資料存取層需整組改為呼叫真實後端 API，而非讀寫瀏覽器 `localStorage`。

### 5.2 建議技術棧（待確認）

- **後端**：Node.js（延續前端 TypeScript 生態，型別可與前端 `src/types.ts` 共用/衍生），框架可選 Express / Fastify / Hono
- **資料庫**：PostgreSQL（關聯式，適合 Phase 1 的活動/時段/回覆/留言這種明確關聯結構）＋ ORM（如 Prisma，可直接從 schema 產生 TypeScript 型別，與前端共用資料模型）
- **託管**：可先用單一雲端服務（如 Render／Railway／Fly.io）快速上線 Phase 1，待流量與需求明確後再評估是否需要更複雜的基礎設施
- **前端部署**：延續現有 GitHub Pages 部署方式，或改為與後端同平台部署，視最終選擇的後端託管方式而定

### 5.3 資料庫 Schema

正式產品建議採用以下正規化資料表：

- **events**：`id`, `title`, `description`, `location_text`, `location_url`, `host_name`（必填）, `host_email`（可為空）, `mode`（`date_only` 或 `time_slots`，建立後不可變更）, `response_deadline`（必填，儲存 UTC 時間戳，顯示時一律轉換為台灣時間）, `status`, `final_slot_id`, `final_note`, `cancelled_at`, `created_at`, `updated_at`
- **time_slots**：`id`, `event_id`（FK）, `date`, `time`（僅 `mode = time_slots` 時有值；`date_only` 模式下為 null，代表整天，彙整時以「日」為單位）, `label`
- **participant_responses**：`id`, `event_id`（FK）, `nickname`, `email`, `comment`, `updated_at`
- **response_availability**：`response_id`（FK）, `slot_id`（FK）, `status`（字串欄位，非資料庫原生 enum 型別；目前 3 個值：available / if_needed / unavailable，需保留未來擴充更多狀態值的彈性，不可用布林值等二元設計實作）— 每筆回覆對每個時段的勾選狀態拆成獨立表，以利查詢與彙整統計
- **event_comments**：`id`, `event_id`（FK）, `nickname`, `message`, `created_at`

不再設計「主揪憑證」相關欄位（如 token／雜湊值）——主揪身分改用 `host_name`／`host_email` 核對，見第 5.4、5.6 節。

### 5.4 API 端點設計

| 方法與路徑 | 說明 |
|---|---|
| `POST /api/events` | 建立活動 |
| `GET /api/events/:id` | 取得活動內容 |
| `POST /api/events/:id/responses` | 送出或更新參與者回覆 |
| `POST /api/events/:id/finalize` | 主揪定案（需驗證主揪身分，見下方說明） |
| `POST /api/events/:id/reopen` | 重新開放投票（需驗證主揪身分） |
| `POST /api/events/:id/cancel` | 取消活動（需驗證主揪身分） |
| `POST /api/events/:id/comments` | 送出留言 |

**主揪身分驗證方式**：上表標註「需驗證主揪身分」的端點，request body 需附上 `host_name`（若該活動建立時有登記 `host_email`，則同時附上 `host_email`）。後端每次都要重新比對這兩個值是否與該活動 `events` 資料表中登記的完全相符（區分大小寫，不做任何寬鬆或模糊比對），驗證通過才能執行操作——不使用 token／session 機制，每次寫入都要重新核對。前端可將使用者輸入過的 `host_name`／`host_email` 存在瀏覽器（例如 localStorage）自動代入以減少重複輸入，但這只是前端體驗優化，安全驗證仍以後端每次核對為準。

### 5.5 通知機制（開放問題，需工程團隊決定）

FR-6（定案通知）與留言通知目前正式產品尚未有實作，需要在 Phase 1 新增。建議方向：Email（資料模型已有 `host_email`／參與者 `email` 欄位可用），可選用 Postmark／Resend／SendGrid 等交易型郵件服務。是否額外支援 LINE Notify（提升與「LINE 一鍵分享」功能的體驗一致性）留待第 6 節開放問題討論。

### 5.6 安全性設計

- 主揪身分驗證：以「主揪姓名＋Email（若有登記）」核對取代任何形式的祕密憑證或 token，比對規則見第 5.4 節。**此設計為 Phase 1 刻意接受的風險**：未登記 Email 的活動，任何知道主揪姓名（＋該活動連結）的人都能取得管理權限；若之後需要更嚴謹的存取控制，需另外規劃（見第 6 節開放問題）
- 活動 ID：需為不可預測值（如 UUID 或高熵亂數），避免被枚舉猜出其他人的活動
- 輸入驗證：所有寫入端點需伺服器端重新驗證（不可只信任前端驗證），標題長度、留言長度等限制皆須在伺服器端強制執行
- 防濫用：投票、留言等公開寫入端點需有基本流量限制，見第 4.3 節 NFR

## 6. 開放問題（工程團隊 kickoff 時需一起決定）

1. 通知管道最終要 Email、LINE Notify，還是兩者都要？
2. 後端／資料庫／託管平台的最終技術選型（第 5.2 節僅為建議）
3. 參與者識別機制：單純「暱稱比對」是否足以辨識重複回覆，還是需要更嚴謹的方式（例如暱稱＋Email 組合唯一性）？
4. 資料保存政策：活動連結失效（7 天後）之後，資料庫記錄要保留多久／是否要提供匯出或刪除機制？
5. Google Maps 短連結：正式產品是否要串接真實的解析服務，還是維持只接受完整網址（不特別處理短連結）？
6. Should-have 項目（第 2.4 節）是否納入 Phase 1 開發範圍，或延到 Phase 1 上線後的下一個迭代？
7. 防濫用機制的具體門檻（同一 IP／來源在多長時間內允許幾次請求）尚未訂出數字，待技術選型後由工程團隊決定
8. 主揪身分驗證目前刻意採用低安全性的姓名／Email 核對（見第 5.6 節），未來是否需要加強（例如簡單的驗證信流程），留待 Phase 1 上線後視情況重新評估
