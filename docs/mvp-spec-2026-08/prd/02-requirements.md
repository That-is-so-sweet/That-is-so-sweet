## 7. User Stories & Requirements

> 依 `user-story` skill 的格式產出：Mike Cohn 的 Use Case（As a / I want to / so that）＋ Gherkin 風格 Acceptance Criteria（Scenario / Given / and Given / When / Then）。每個 Scenario 只有一個 When、一個 Then；需要涵蓋的例外情境拆成獨立 Scenario，而不是塞進同一個 When/Then。以下的驗證規則（長度限制、狀態阻擋條件等）是團隊已經確認過的既有行為，而非新的假設，因此可以直接照此開發與測試，不需要再另外驗證。

### Epic Hypothesis

我們相信，如果用一個免登入、免加好友的時間投票連結取代 LINE 群組裡人工喬時間，主揪的決策時間可以從平均 5 天大幅縮短，參與者的回覆意願與速度也會提升，因為參與門檻降低了。我們會透過 Phase 1 上線後的實際使用數據（定案天數、投票完成率、連結轉換率，見[第一部分 Success Metrics](./01-overview.md#怎麼知道有沒有成功)）驗證這個假設是否成立。

### User Story 001：建立活動並取得分享連結

- **Summary**：讓主揪一步建立活動並立即拿到可分享連結，取代手動整理時間表

#### Use Case

- **As a** 主揪
- **I want to** 填寫活動名稱、我的姓名、候選時段與回覆截止時間後送出
- **so that** 我能立即拿到一個可以直接分享出去的連結，不用自己整理時間表傳給朋友

#### Acceptance Criteria

**Scenario 1：成功建立活動並取得連結**
- **Given** 我是第一次使用揪甘心的主揪（未登入）
- **and Given** 我已經填寫活動名稱「八月聚餐」、我的姓名，並選擇了候選時段模式（純日期或指定時間，兩者擇一）
- **and Given** 我已經新增至少 1 個候選時段，並填寫了回覆截止時間
- **When** 我點擊「建立活動」送出表單
- **Then** 系統立即產生一個可分享的活動連結；之後可用我填寫的姓名（若有填 Email 則需一併核對）取得管理權限

**Scenario 2：活動名稱為空時阻擋送出**
- **Given** 我在建立活動表單中
- **and Given** 活動名稱欄位是空的
- **When** 我點擊「建立活動」
- **Then** 系統阻擋送出，並提示「請輸入活動名稱」

**Scenario 3：活動名稱超過長度上限時阻擋送出**
- **Given** 我在建立活動表單中
- **and Given** 我輸入的活動名稱超過 30 字
- **When** 我點擊「建立活動」
- **Then** 系統阻擋送出，並提示名稱長度超過上限

**Scenario 4：沒有任何候選時段時阻擋送出**
- **Given** 我在建立活動表單中
- **and Given** 我尚未新增任何候選時段
- **When** 我點擊「建立活動」
- **Then** 系統阻擋送出，並提示「請至少新增一個候選時段」

**Scenario 5：主揪姓名為空時阻擋送出**
- **Given** 我在建立活動表單中
- **and Given** 主揪姓名欄位是空的
- **When** 我點擊「建立活動」
- **Then** 系統阻擋送出，並提示「請輸入您的姓名」（此欄位日後將用於身分驗證，見 Story 004）

**Scenario 6：回覆截止時間未填時阻擋送出**
- **Given** 我在建立活動表單中
- **and Given** 回覆截止時間欄位是空的
- **When** 我點擊「建立活動」
- **Then** 系統阻擋送出，並提示「請設定回覆截止時間」（此欄位為必填，所有時間以台灣時間認定）

**Scenario 7：填寫主揪 Email 時系統寄送通知信**
- **Given** 我在建立活動表單中額外填寫了 Email
- **When** 我點擊「建立活動」且成功送出
- **Then** 系統寄送一封含活動分享連結的通知信到我填寫的 Email

**Scenario 8：主揪姓名超過長度上限時阻擋送出**
- **Given** 我在建立活動表單中
- **and Given** 我輸入的主揪姓名超過 20 字
- **When** 我點擊「建立活動」
- **Then** 系統阻擋送出，並提示「姓名不可超過 20 字」

**Scenario 9：主揪 Email 格式不正確時阻擋送出**
- **Given** 我在建立活動表單中填寫了 Email，但格式不正確（例如缺少 @ 符號）
- **When** 我點擊「建立活動」
- **Then** 系統阻擋送出，並提示「Email 格式不正確」

**Scenario 10：回覆截止時間早於現在時阻擋送出**
- **Given** 我在建立活動表單中
- **and Given** 我選擇的回覆截止時間早於目前時間
- **When** 我點擊「建立活動」
- **Then** 系統阻擋送出，並提示「截止時間需晚於目前時間」

### User Story 002：免登入投票

- **Summary**：讓參與者免加好友、免登入就能勾選可行時段，降低回覆門檻

#### Use Case

- **As a** 參與者
- **I want to** 點開活動連結後直接輸入暱稱並勾選時段
- **so that** 我不用加好友、不用註冊帳號也能快速回覆我的可行時間

#### Acceptance Criteria

**Scenario 1：首次填寫並成功送出投票**
- **Given** 我點開一個狀態為「進行中」且尚未截止投票的活動連結
- **and Given** 我輸入了暱稱「小明」
- **and Given** 我針對每個候選時段都選擇了可行／可能可以／不可行其中一項
- **When** 我點擊送出
- **Then** 系統記錄我的回覆，並在彙整結果中顯示我的暱稱與勾選狀態

**Scenario 2：用同一個暱稱修改先前的回覆**
- **Given** 我先前已經用暱稱「小明」送出過一次回覆
- **and Given** 我再次點開同一個活動連結並輸入同樣的暱稱「小明」
- **When** 我修改其中一個時段的勾選狀態並送出
- **Then** 系統更新我原本的那筆回覆，而不是新增一筆重複紀錄（暱稱比對的嚴謹度目前仍是待決事項，見[第三部分開放問題](./03-planning.md)）

**Scenario 3：活動已取消時阻擋投票**
- **Given** 活動狀態已經是「已取消」
- **When** 我嘗試送出投票
- **Then** 系統阻擋送出，並提示活動已由主揪取消

**Scenario 4：活動已定案時阻擋投票**
- **Given** 活動狀態已經是「已定案」
- **When** 我嘗試送出投票
- **Then** 系統阻擋送出，並提示活動時間已由主揪拍板定案

**Scenario 5：投票已截止時阻擋投票**
- **Given** 活動狀態仍是「進行中」
- **and Given** 目前時間已經超過活動的回覆截止時間
- **When** 我嘗試送出投票
- **Then** 系統阻擋送出，並提示投票已截止、請聯繫主揪重新開放

**Scenario 6：有候選時段未勾選時阻擋送出**
- **Given** 我輸入了暱稱，且這個活動有 3 個候選時段
- **and Given** 我只針對其中 2 個候選時段選擇了可行狀態，第 3 個尚未選擇
- **When** 我點擊送出
- **Then** 系統阻擋送出，並提示「請完成所有時段的勾選」（系統不提供任何預設值，避免虛報可行時段）

**Scenario 7：設定密碼保護我的回覆**
- **Given** 我第一次用暱稱「小明」送出投票
- **and Given** 我額外填寫了密碼
- **When** 我送出投票
- **Then** 系統記錄這筆回覆，並將密碼雜湊後儲存；之後任何人要用「小明」這個暱稱修改回覆，都需要輸入相同密碼

**Scenario 8：密碼不正確時阻擋修改既有回覆**
- **Given** 暱稱「小明」的回覆先前已經設定過密碼
- **and Given** 我再次點開同一個活動連結，輸入暱稱「小明」，但密碼輸入錯誤（或留空）
- **When** 我修改勾選狀態並送出
- **Then** 系統阻擋送出，並提示「密碼不正確，暫時無法查看或編輯這個暱稱的既有回覆」，不會覆蓋原本的回覆

**Scenario 9：未設定密碼的暱稱可被任何人覆蓋**
- **Given** 暱稱「小華」的回覆先前送出時沒有設定密碼
- **and Given** 我點開同一個活動連結，輸入同樣的暱稱「小華」
- **When** 我修改勾選狀態並送出（不需輸入任何密碼）
- **Then** 系統直接更新「小華」原本的回覆（此為刻意的設計，密碼保護是選填、非強制）

**Scenario 10：依星期幾批次勾選候選時段**
- **Given** 這個活動有超過 10 個候選時段，橫跨平日與週末
- **and Given** 我選擇篩選條件「週末」
- **When** 我對篩選出的時段一次套用「可行」
- **Then** 系統把所有週末的候選時段都設為可行，我不需要逐一勾選

**Scenario 11：切換清單／行事曆檢視**
- **Given** 我正在勾選候選時段
- **When** 我把畫面從「清單檢視」切換到「行事曆檢視」
- **Then** 畫面改用月曆網格呈現同一份候選時段，我目前的勾選狀態不會遺失

### User Story 003：查看彙整結果

- **Summary**：讓主揪一眼看到所有人彙整後的可行時段熱度，不用自己手動比對

#### Use Case

- **As a** 主揪
- **I want to** 打開活動頁面看到每個候選時段的彙整統計
- **so that** 我不用自己一筆筆對照每個人的回覆

#### Acceptance Criteria

**Scenario 1：有多筆回覆時顯示彙整統計**
- **Given** 活動已經收到至少 1 筆參與者回覆
- **When** 我（主揪）打開活動頁面的彙整結果畫面
- **Then** 每個候選時段都顯示可行／可能可以／不可行的人數與對應名單

**Scenario 2：尚無任何回覆時的顯示**
- **Given** 活動目前還沒有收到任何參與者回覆
- **When** 我打開彙整結果畫面
- **Then** 畫面清楚顯示「尚無人回覆」，而不是空白或錯誤畫面

**Scenario 3：新回覆送出後彙整結果更新**
- **Given** 我正在查看彙整結果畫面
- **and Given** 有新的參與者剛送出一筆回覆
- **When** 我重新整理頁面
- **Then** 彙整結果反映最新送出的那筆回覆（不強制即時推播，重新整理後更新即符合本 Story）

**Scenario 4：切換清單／行事曆檢視**
- **Given** 我正在查看彙整結果畫面
- **When** 我把畫面從「清單檢視」切換到「行事曆檢視」
- **Then** 畫面改用月曆網格呈現同一份彙整統計，資料內容不變

### User Story 004：一鍵定案

- **Summary**：讓主揪從彙整結果直接選定最終時段並一鍵確認，不用再回群組宣布一次

#### Use Case

- **As a** 主揪
- **I want to** 從候選時段中選定最終時段並確認
- **so that** 我不用再回 LINE 群組另外宣布一次結果

#### Acceptance Criteria

**Scenario 1：主揪成功定案**
- **Given** 我輸入的姓名（若活動有登記 Email，則加上 Email）與建立活動時登記的資料完全相符（區分大小寫）
- **and Given** 我選定了一個屬於此活動候選清單中的時段
- **When** 我點擊「確認定案」（可選填備註）
- **Then** 活動狀態變更為「已定案」，且該時段被記錄為最終時段

**Scenario 2：非主揪嘗試定案被拒絕**
- **Given** 我輸入的姓名（或 Email）與這個活動登記的主揪資料不相符
- **When** 我嘗試呼叫定案操作
- **Then** 系統拒絕操作，並回應身分驗證失敗（此為 Phase 1 刻意採用的低安全性設計，未登記 Email 的活動僅以姓名核對，見 [SPEC.md 第 5.6 節](../SPEC.md#56-安全性設計)）

**Scenario 3：選擇了不存在於候選清單的時段**
- **Given** 我通過主揪身分驗證
- **and Given** 我提交的最終時段 ID 不在此活動的候選時段清單中
- **When** 我點擊「確認定案」
- **Then** 系統阻擋操作，並提示所選的最終時段無效

**Scenario 4：活動已取消時無法定案**
- **Given** 活動狀態已經是「已取消」
- **When** 我（主揪）嘗試定案
- **Then** 系統阻擋操作，並提示活動已取消、無法拍板定案

**Scenario 5：定案後出席名單只計入勾選「可行」的參與者**
- **Given** 活動已經定案，最終時段是 8/30 19:00
- **and Given** 小明對這個時段勾選「可行」，小華對這個時段勾選「可能可以」
- **When** 我（主揪）查看定案後的出席名單
- **Then** 出席名單只列出小明，不列出小華；小華仍會依 Story 005 收到定案通知，只是不計入出席名單的統計

### User Story 005：定案通知

- **Summary**：主揪定案後系統自動通知所有已回覆的參與者，避免有人錯過確定的時間

#### Use Case

- **As a** 參與者
- **I want to** 在主揪定案後自動收到通知
- **so that** 我不會因為沒有回頭確認活動頁面而錯過已經確定的時間

#### Acceptance Criteria

**Scenario 1：定案後成功發送通知**
- **Given** 主揪剛完成定案操作
- **and Given** 有參與者在回覆時留下了聯絡方式（Email）
- **When** 系統處理定案後續流程
- **Then** 系統對每一位留下聯絡方式的參與者發送通知，內容包含最終時間、地點與備註

**Scenario 2：參與者未留聯絡方式時不強制發送**
- **Given** 某位參與者送出回覆時沒有填寫 Email
- **When** 定案通知發送流程執行
- **Then** 系統不會嘗試對這位參與者發送通知，也不會因此讓整體流程失敗

**Scenario 3：通知發送失敗時的處理**
- **Given** 定案通知正在對外發送
- **and Given** 其中一封通知因為外部服務錯誤而發送失敗
- **When** 系統偵測到這次發送失敗
- **Then** 系統記錄這筆失敗（可供之後排查），而不是靜默略過或讓整個定案操作失敗回滾

> 通知管道（Email／LINE Notify）尚未選定，見下方 Dependencies；上述 Scenario 是通知邏輯本身的需求，不預設特定管道的實作細節。

### User Story 006：活動狀態管理（取消／重新開放）

- **Summary**：讓主揪在計畫有變時可以取消活動或重新開放投票，不用整個活動重來一次

#### Use Case

- **As a** 主揪
- **I want to** 取消活動或把已定案的活動改回進行中
- **so that** 計畫有變時我不用整個活動重新建立一次

#### Acceptance Criteria

**Scenario 1：主揪成功取消活動**
- **Given** 我通過主揪身分驗證
- **and Given** 活動目前不是「已取消」狀態
- **When** 我執行取消操作
- **Then** 活動狀態變更為「已取消」，且已回覆的參與者會收到取消通知

**Scenario 2：重複取消已取消的活動**
- **Given** 活動狀態已經是「已取消」
- **When** 我（主揪）再次嘗試取消
- **Then** 系統阻擋操作，並提示活動已經取消過了

**Scenario 3：主揪把已定案的活動重新開放投票**
- **Given** 活動狀態目前是「已定案」
- **and Given** 我通過主揪身分驗證
- **When** 我執行「重新開放」操作
- **Then** 活動狀態變更回「進行中」，先前的最終時段設定被清除，且系統確保回覆截止時間仍在未來（若原本已過期則自動順延）

**Scenario 4：連結超過失效期限**
- **Given** 活動狀態是「已定案」
- **and Given** 最終時段的日期距今已經超過 7 天
- **When** 任何人（包含主揪）開啟這個活動連結
- **Then** 系統顯示明確的「連結已失效」畫面，而非一般錯誤或空白頁面

### User Story 007：留言互動（含提示）

- **Summary**：讓參與者與主揪能在活動頁面留言溝通細節，並在留言前提醒會觸發通知

#### Use Case

- **As a** 參與者
- **I want to** 在活動頁面留言
- **so that** 我可以跟主揪或其他人溝通細節，不用另外開一個群組

#### Acceptance Criteria

**Scenario 1：成功送出留言**
- **Given** 活動連結尚未失效（見 Story 006 的失效規則）
- **and Given** 我輸入了暱稱與留言內容（未超過長度上限）
- **When** 我點擊送出留言
- **Then** 留言出現在活動頁面的留言列表中

**Scenario 2：留言區持續顯示通知提示**
- **Given** 我打開了活動頁面的留言區塊
- **When** 我看到留言輸入欄位
- **Then** 欄位上方持續顯示「在這邊留言會被寄信喔，請留下想讓大家看到的內容」，不需要先點擊或聚焦欄位才出現，避免我誤以為只是內部備註（對應 [UX 回饋 PLAN.md 第 4 項](../../ux-feedback-2026-08/PLAN.md)）

**Scenario 3：留言內容超過長度上限**
- **Given** 我輸入的留言內容超過 300 字
- **When** 我點擊送出
- **Then** 系統阻擋送出，並提示留言內容過長

**Scenario 4：暱稱為空或超過長度上限時阻擋送出**
- **Given** 留言的暱稱欄位是空的，或輸入超過 20 字
- **When** 我點擊送出留言
- **Then** 系統阻擋送出，並提示「請輸入您的暱稱」或「暱稱不可超過 20 字」

**Scenario 5：活動已取消時阻擋留言**
- **Given** 活動狀態已經是「已取消」
- **When** 我嘗試送出留言
- **Then** 系統立即阻擋送出，並提示「此活動已取消，無法再留言」；此活動先前已存在的留言仍可瀏覽

---

### Constraints & Edge Cases（跨 Story 的補充說明）

- **技術限制**：目前完全沒有後端／資料庫／通知機制，Phase 1 等於要從零建置整套後端（見 [SPEC.md 第 5 節](../SPEC.md)建議架構）
- **邊界情況彙總**：上述各 Story 的 Scenario 已涵蓋主要邊界情況；跨 Story 共通的例外有兩個守門條件——「活動連結已失效」（見 Story 006 Scenario 4）一旦觸發會擋掉投票、留言、查看彙整等所有互動；「活動已取消」則會立即擋掉投票（Story 002 Scenario 3）與留言（Story 007 Scenario 5），但不等同於連結失效，已存在的內容仍可瀏覽，兩者判斷邏輯彼此獨立，不可混用

## 8. Out of Scope

### Not Included in This Release（Phase 1）

- **快閃聊天室、AI 選餐廳、分帳功能** — 屬於 Phase 2「減輕主揪壓力」，Phase 1 只驗證核心喬時間假設，避免資源分散
- **飲食護照、菜單翻譯、邀請函等進階功能** — 屬於 Phase 3「提升聚會體驗」，需等核心成團問題解決、假設驗證成立後再評估
- **跨平台行事曆自動同步** — 明確排除；單向「加入行事曆」匯出連結不在排除範圍內，是可視資源併入 Phase 1 的小功能

### Future Considerations（Should-have，視 Phase 1 資源決定是否納入，非必要不做）

- 未回覆者的提醒通知
- 時段衝突時的次佳選項建議

> 這兩項的評分與排序、以及 Phase 2／Phase 3 六個候選 Epic 的完整展開，見[第三部分](./03-planning.md)。

> 「可能可以／暫定」的彈性回覆選項已確定為 Phase 1 must-have，不在此候選清單中，詳見 Story 002 與 [SPEC.md FR-3](../SPEC.md)。

## 9. Dependencies & Risks

### Dependencies

- **Technical**：需要新建後端 API 服務與關聯式資料庫，見 [SPEC.md 第 5 節](../SPEC.md#5-建議技術架構草案待工程團隊定案)的建議架構草案
- **External**：通知寄送服務尚未選定（Email provider，或是否也要支援 LINE Notify）——見[第三部分開放問題](./03-planning.md)
- **Team**：工程團隊 kickoff 需要對齊 SPEC.md 的技術架構建議；設計端需確認是否要出一版正式視覺稿

### Risks & Mitigations

- **Value risk**：核心假設本身可能不成立——如果使用者普遍覺得「在 LINE 群組裡問一下」比「打開新連結」更省事，或多數參與者仍傾向直接留言回覆而非使用勾選介面，遷移成本會蓋過新體驗價值（見[第一部分](./01-overview.md)「問題」的推翻條件）
  - **Mitigation**：Phase 1 上線後緊盯「定案天數」與「投票完成率」兩個核心指標；如果不如預期，優先重新檢視核心互動設計，而不是急著加新功能
- **Usability risk**：新增的免登入識別機制（暱稱＋Email）可能造成新的摩擦點，或讓參與者搞混自己先前的回覆
  - **Mitigation**：對應 [docs/ux-feedback-2026-08/PLAN.md](../../ux-feedback-2026-08/PLAN.md) 子專案 B 正在處理的項目，Phase 1 開發時需要一併納入設計
- **Feasibility risk**：目前沒有任何後端／資料庫／通知機制，屬於從零建置
  - **Mitigation**：依 SPEC.md 建議架構分階段實作，優先做出最小可行後端，不追求一次到位
- **Security risk**：主揪身分驗證採用姓名（＋Email，若有登記）核對，不是帳號密碼或高熵憑證；未登記 Email 的活動，任何知道主揪姓名與活動連結的人都能取得管理權限，這是 Phase 1 刻意接受的風險（見 [SPEC.md 第 5.6 節](../SPEC.md#56-安全性設計)）
  - **Mitigation**：上線後留意是否發生管理權限被冒用的實際案例，若發生率高於預期，優先評估加上簡單的驗證信流程（見[第三部分開放問題](./03-planning.md)）
- **Viability risk**：商業模式與資源投入尚未定案（見[第一部分](./01-overview.md)、[第三部分](./03-planning.md)開放問題）
  - **Mitigation**：與利害關係人確認 Phase 1 的資源與時程承諾後，再正式排入工程排程
